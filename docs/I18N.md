# Translations (build-time)

Write English once, in `i18n/en.json`. Arabic lives in `i18n/ar.json`. The site reads `js/translations.js`, which is generated from those two files. Nothing is translated in the browser, so there is no API key on the site and it stays fully static.

## Adding or changing text
1. Edit the English text in `i18n/en.json` (add a new key if needed) and put `data-i18n="your.key"` on the element in `index.html`.
2. Run, from the repo root (Node 18+):
   `DEEPL_API_KEY=... node scripts/i18n.mjs translate`
   or `I18N_PROVIDER=openai OPENAI_API_KEY=... node scripts/i18n.mjs translate`
   Only new or changed English keys are sent to the API.
3. Read the new Arabic in `i18n/ar.json`, fix anything you like by hand.
4. Commit `i18n/*`, `js/translations.js` and `index.html`, then push.

## Rules
- If you edit an Arabic value by hand, the tool will never overwrite it (it compares against `i18n/state.json`). To get a fresh machine translation of that key, delete its entry from `ar.json`.
- `node scripts/i18n.mjs check` validates keys and that `js/translations.js` is up to date (no network). `translate --dry-run` lists what would be sent.
- Product names in `i18n/config.json` (`preserveTerms`) are kept as-is.
- `js/translations.js` is generated: never edit it. It is committed because GitHub Pages has no build step.
- The English text inside `index.html` is only a fallback if JavaScript is off. At runtime the text comes from `en.json`.
- Never commit an API key.
